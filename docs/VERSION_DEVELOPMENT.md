# 版本驱动开发规范（强制）

用户确认：2026-11-26。适用于基座及后续采用本规范的应用。

1. 任一项目同一时刻只允许一个活动开发版本。版本立项须固定目标、任务范围、基线、验收标准及唯一交付候选。新功能需求进入下一版本需求池，不得在当前版本期间实现、开新功能分支或合并下一版本。
2. 同版本任务可拆分提交或 PR，但统一集成到该版本分支，只有统一候选进入 preview。当前版本缺陷可在本版本修复；新增范围须经用户明确批准。正式运行严重故障可受控 hotfix，先暂停活动版本并重新核验基线。
3. 上一版本正式 main 发布、真实部署及验收证据核实后才启动下一版本。保留后续版本已有分支和草稿，禁止将其当作当前交付候选。不得为解除阻塞伪造测试、审查或验收。
4. 测试：开发期间按模块专项测试，版本候选完整回归；GitHub Actions 仅为用户授权的备用隔离测试，不执行发布、不冒充 MacCI 回执。避免重复测试、无关构建及空跑。正式宿主测试、授权、preview 验收、main 发布门禁保留。
5. 每小时报告真实新增功能、提交、测试、合并、部署和验收；分别核实，不以计划、状态查询或 PR 数量充当交付。禁止修改生产数据库。
6. 当前执行清单见 [版本计划](RELEASE_PLAN.md)。本规范现阶段为开发管理规则，并非已实现的调度器强制门禁；自动版本门禁属于后续需求。

## 版本完成时的 README 整体维护（强制）

用户确认：2026-11-27。每个新版本功能开发完成后，正式发布前必须以该版本实际实现为依据，通读并重新组织根目录 README.md，而非仅在末尾追加版本说明。

- 更新项目定位、当前版本及功能总览、系统架构、支持平台与依赖、快速开始、初始化/部署/升级/回滚、日常运维、安全与权限、开发测试及文档导航；按实际需要合并、移动或删除过时和重复章节。
- 核对示例命令、配置名称、路径、链接及版本信息与候选代码一致；未实现或未验证的能力明确标记，不把规划描述为现有功能。
- 历史版本细节移至既有更新记录、release_notes 或独立文档，保留必要历史证据；README 聚焦当前版本的使用和理解，不成为流水账。
- README 整体更新纳入同一版本候选的 diff 与发布检查清单，核查内容完整性、内部链接、命令及兼容性；不允许仅追加变更日志即视为完成。不额外触发无关构建，文档与实际功能统一交付。
- 此规范适用于基座及后续采用本规范的应用。V0.5.0 起执行；未完成 README 更新的版本不得标记开发交付完成。现阶段为人工/Agent 强制检查项，不宣称已具备自动门禁。
